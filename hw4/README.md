# ДЗ 4 — база данных и транзакции

В этом задании API магазина из [ДЗ 2](../hw2/hw/README.md) переведён на хранение данных в базе. Товары, корзины и состав корзин сохраняются в PostgreSQL 16. Для работы с базой используется SQLAlchemy, таблицы создаются при запуске приложения.

Отдельно в `isolation_demo.py` собраны примеры аномалий транзакций. Условия задания находятся в [lecture4/README.md](../lecture4/README.md).

## Как запустить

Из корня репозитория:

```sh
cd hw4
docker compose up --build -d
docker compose ps
```

Дальше все команды выполняются из папки `hw4`. Если на порту `8080` ещё работает ДЗ 3, сначала нужно остановить его контейнеры.

После запуска Swagger будет доступен по адресу [localhost:8080/docs](http://localhost:8080/docs). Через него можно создавать товары и корзины, добавлять товары в корзину и проверять остальные методы API.

К базе с компьютера можно подключиться по адресу `localhost:5433`. Название базы, логин и пароль — `shop`. Сам API подключается к ней внутри Docker по адресу `db:5432`; строка подключения задана в `DATABASE_URL` в Compose.

Если что-то не запустилось, логи можно посмотреть так:

```sh
docker compose logs --tail 100 api db
```

## Как проверить сохранение данных

1. Создать товар через `POST /item`, например с телом `{"name": "Notebook", "price": 120}`. Сохранить его `id` из ответа.
2. Создать корзину через `POST /cart` и добавить в неё товар через `POST /cart/{cart_id}/add/{item_id}`.
3. Перезапустить API командой `docker compose restart api`.
4. Запросить товар и корзину через `GET /item/{id}` и `GET /cart/{id}`. Данные должны остаться на месте.

Можно также пересоздать контейнеры:

```sh
docker compose down
docker compose up -d
```

После этого товар и корзина по тем же `id` тоже должны быть доступны: PostgreSQL хранит данные в Docker-томе `shop_data`.

Для обычной остановки достаточно `docker compose down`. Если нужно удалить и данные, используется `docker compose down -v`.

## Уровни изоляции

Когда API и база запущены, примеры можно выполнить одной командой:

```sh
docker compose exec api python /app/hw4/isolation_demo.py
```

В каждом примере участвуют две транзакции с отдельными подключениями к базе. Скрипт выполняет их действия в заданном порядке и проверяет результат. Для примеров создаётся временная схема, которая удаляется в конце. Товары и корзины при этом не затрагиваются.

Всего проверяется девять сценариев:

| Аномалия | Что происходит в PostgreSQL |
| --- | --- |
| Dirty read | Ни на Read Uncommitted, ни на Read Committed нельзя прочитать чужое изменение до его фиксации. |
| Non-repeatable read | На Read Committed повторное чтение видит новое значение после чужого commit. На Repeatable Read значение остаётся прежним. |
| Phantom read | На Read Committed повторный запрос видит добавленную строку. На Repeatable Read и Serializable набор строк не меняется. |
| Write skew | На Repeatable Read обе транзакции могут завершиться и вместе нарушить общее условие. На Serializable одна из них получает ошибку `40001`. |

Write skew показан на примере двух дежурных врачей. Каждый видит, что на смене есть ещё один врач, и уходит. На Repeatable Read оба изменения сохраняются, поэтому дежурных не остаётся. На Serializable одна транзакция отклоняется. Скрипт повторяет её целиком: она уже видит, что врач остался один, и не снимает его с дежурства.

В задании предлагается показать dirty read на Read Uncommitted и phantom read на Repeatable Read, но в PostgreSQL эти аномалии на указанных уровнях не возникают. Read Uncommitted здесь работает как Read Committed, а Repeatable Read защищает и от фантомов. Поэтому примеры показывают поведение именно PostgreSQL.

Если все проверки прошли, в конце появится сообщение:

```text
All 9 isolation scenarios passed
```

## Без Docker

Сам API можно запустить локально: установить зависимости из `hw4/requirements.txt`, добавить `hw2/hw` в `PYTHONPATH` и выполнить `uvicorn shop_api.main:app --port 8080` из корня репозитория. Если `DATABASE_URL` не задан, данные сохраняются в локальном файле SQLite.

Для примеров изоляции нужен PostgreSQL. При локальном запуске скрипта адрес базы задаётся через `DATABASE_URL` или аргумент `--database-url`.
