# ДЗ 4: База данных + уровни изоляции транзакций

Добавляет персистентное хранение (MySQL) в сервис `shop_api` из
[hw2](../hw2/hw) и демонстрирует поведение разных уровней изоляции
транзакций, по аналогии с [lecture4](../lecture4).

## 1. База данных в docker-compose

MySQL добавлен как отдельный сервис в [hw3/docker-compose.yml](../hw3/docker-compose.yml)
(там же поднимается сервис `local` - он теперь ходит в БД вместо
in-memory словарей):

```bash
cd hw3
docker compose up --build
```

MySQL доступен:
- изнутри docker-сети (для сервиса `local`) - `mysql:3306`;
- снаружи (для локальных скриптов и `pytest` без Docker) - `localhost:3307`.

Таблицы (`items`, `carts`, `cart_items`) создаются автоматически при
импорте `shop_api.main` (`Base.metadata.create_all`).

## 2. Код, работающий с БД

`shop_api/main.py` теперь ходит в MySQL через SQLAlchemy
(`shop_api/db.py`) вместо словарей в памяти. Все HTTP-ручки и их
поведение (коды ответов, валидация, фильтры) не изменились - поменялось
только хранилище.

Чтобы прогнать `pytest` локально без полного стека, достаточно поднять
только MySQL (`docker compose up mysql` из `hw3/`) и перед запуском тестов
указать адрес БД:

```powershell
$env:DATABASE_URL = "mysql+pymysql://shop:shop@localhost:3307/shop_api"
pytest hw2/hw
```

Если `DATABASE_URL` не задана, используется то же значение по умолчанию.

## 3. Демонстрация уровней изоляции

Скрипты лежат в `hw4/isolation_demos/` и используют отдельные от API
таблицы (`demo_accounts`, `demo_products`) в той же базе. Каждый сценарий
запускает две настоящие параллельные транзакции (в отдельных потоках) с
детерминированной синхронизацией шагов, чтобы надёжно воспроизвести нужное
чередование.

Запуск (из корня репозитория, MySQL должен быть поднят на `localhost:3307`):

```bash
python -m hw4.isolation_demos.dirty_read
python -m hw4.isolation_demos.non_repeatable_read
python -m hw4.isolation_demos.phantom_read
```

Что показывает каждый скрипт:

- **dirty_read.py** - при `READ UNCOMMITTED` транзакция A видит ещё не
  закоммиченное (и затем откатываемое) изменение B; при `READ COMMITTED`
  - не видит.
- **non_repeatable_read.py** - при `READ COMMITTED` повторный `SELECT` в
  той же транзакции A видит уже закоммиченное изменение B (значение
  "уехало"); при `REPEATABLE READ` - оба чтения совпадают.
- **phantom_read.py** - особенность InnoDB: обычный `SELECT` под
  `REPEATABLE READ` не видит новые строки благодаря MVCC-снэпшоту, но
  последующий `UPDATE` по тому же условию делает "текущее" чтение и всё
  же задевает их - расхождение между числом из `SELECT` и числом
  затронутых `UPDATE` строк и есть фантом. Под `SERIALIZABLE` обычный
  `SELECT` становится блокирующим, поэтому `INSERT` из другой транзакции
  просто ждёт коммита A - фантому неоткуда взяться.

Каждый скрипт печатает пошаговый лог обеих транзакций и итоговый вердикт
("ДА, ... произошёл" / "НЕТ, ... не было"). Для сдачи ДЗ приложите вывод
(скриншот терминала или лог) каждого из трёх скриптов.
